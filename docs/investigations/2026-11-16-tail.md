# Backend tail latency and prefix feedback

Investigated November 16, 2026, against source `5753f7a`, the saved
19:30 UTC three-provider cloud run, and its deployed backend binary
`10999570a084bd6a7960db89a087b8874cd9963cf28996e62e02ead47c1ec2a6`.
Read-only diagnostics; no slot deployment, route change, capacity change,
scan, restart or load test. Six additional loopback searches were sequential
and five seconds apart. No Tern or Bluesky search requests were added.

## What the tail measures

The public p90 was 557 ms; the backend-handler p90 was 498.398 ms.
These are quantiles of their own samples, not additive components. The same
`nate` request occupies both percentile positions in this run.

The `nate` request matches Logfire trace
`f6f51b9d2d18a76b7752798fffc22497` by CF-Ray `a5b8f2e6c9147a02`.
Its public handler took 520 ms: cache lookup 6 ms, transport headers 514 ms.
The transport took 508 ms waiting for Fly; its 9 ms route validation ran
alongside that fetch. Worker statistics writes start after the response-path
work and must not be added to it. Native trace sampling is partial; the
saved response headers cover all 40 Typeahead requests.

The backend timer in `services/tantivy/src/server.rs` starts after admission,
before `spawn_blocking`, and ends after response construction. It includes
thread-pool wait, normalization, retrieval, hydration and moderation. It is
not a measurement of Tantivy CPU execution alone. Rust search stages do not
currently emit their own Logfire spans.

## Background I/O is the strongest lead

Fly's historical 15-second samples show average CPU I/O wait jumping from
roughly 0.1–0.2% before 19:34:45 UTC to 17.85–46.87% through 19:37:30.
CPU quota throttling remained exactly zero throughout 19:29–19:42; burst
balance stayed above 195,908 centiseconds, close to its 200,000 maximum.
CPU-credit exhaustion does not explain this run.

At 19:37:19.745 UTC, Logfire records slot A completing a scan of 13,336,047
records in 150,299 ms. That places the scan at approximately 19:34:49–19:37:19,
covering the first sustained I/O-wait spike and four of the five slowest
requests. `services/src/store_process/corpus.zig` confirms that it opens a
read-only store handle and scans the entire actor range for statistics.
The scanner, ongoing store updates and Tantivy share the same machine and disk.

A second spike reaches 39.03% I/O wait in the interval ending 19:39:00 and
30.68% in the next interval, around the 1,664 ms `jola.dev` request.
The responsible writer for this second spike is not identified. Neither
15-second VM metrics nor the existing handler timer can attribute each
request's stalls to one background operation.

Six later loopback checks took 1.074–14.892 ms in the same binary. They visited
2–14 candidates, opened 14–16 scorers over 7–8 segments, and spent
0.127–1.487 ms hydrating results. Process-wide fault and disk-read counters
increased around five checks; concurrent index work shares those counters.
The second `jola.dev` check had no additional major faults or disk reads.
These checks support a cache/I/O hypothesis but do not reproduce or explain
the earlier stalls by themselves.

The next isolated experiment should compare search latency during and outside
the corpus scan on the standby, retaining matching results. Incremental corpus
counts would avoid that full scan; pacing scans and limiting their I/O is a
smaller alternative to test. Measure backend queue wait, retrieval, hydration,
thread CPU and page faults on the same request before choosing a fix. Do not
assume changing the index library removes shared-disk interference.

[Fly metrics documentation](https://fly.io/docs/monitoring/metrics/) defines
the CPU counters in centiseconds and disk timers in milliseconds.
[CPU performance](https://fly.io/docs/machines/cpu-performance/) distinguishes
quota throttling from steal. The derived percentages divide the summed
per-CPU deltas by elapsed seconds and four CPUs.

## Feedback from the aka.dad thread

Fetched the root and every returned branch of
[the thread](https://bsky.app/profile/aka.dad/post/3n2gtmfdcek2q): 23 visible
posts, with returned direct-reply counts matching every post's reported count.
Deleted or blocked content cannot be recovered from that API response.

- Handle versus display-name priority is a concrete caller need. The current
  query merges their matches and orders prefixes by stored quality; it has
  no caller-selectable handle preference. Consider an explicit preference
  rather than a named-account exception.
- Evaluate the progression `aka` → `aka.` → `aka.dad`, plus `quill` and the
  competing handles. A six-query diagnostic confirmed `aka.dad` is absent
  from our top ten for `aka`, while `quillmatiq.com` is first for `quill`.
  Exact-handle checks alone miss this kind of ranking complaint. Add labeled
  prefix cases in a separately versioned corpus, preserving old score meaning.
- A URL-oriented mobile keyboard would make the dot available without a mode
  switch. The homepage search input currently has no `inputmode`, explicit
  autocapitalization setting or spellcheck setting. Use `inputmode="url"`
  for handle-specific fields; general display-name search needs Unicode and
  spaces, so verify both uses on a phone.
- The typo reply supplies no evidence for adding fuzzy matching or ranking
  one person first globally. Popularity is not a relevance oracle for every
  user's intended account.
